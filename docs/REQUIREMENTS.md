# DLsite Coupon Plus — 需求与技术现状说明

> 本文用于向外部征求方案建议。所有数字均为实测，不是估算。
> 最后更新：2026-11-07

## 1. 一句话

给 DLsite 做一层「券后价 + 历史低位 + 套装分摊」的判断层，由**浏览器插件**在作品页直接展示，**站点**提供历史数据与跨作品榜单。

## 2. 要解决的问题

DLsite 的价格有三层叠加，用户无法直观判断"现在是不是该买"：

1. **单品折扣**：页面上直接显示（如 1,210 → 605）
2. **套装折扣（セット割）**：满 N 件打 X 折，折扣率按**定価**算，且**不与单品折扣叠加**（取较大者）
3. **优惠券**：全站券 / 作品券 / 社团券，各有限制条件

用户的实际问题只有一个：**现在这个价，是不是历史低位？**

回答它需要三样东西：历史价格序列、当前券后价、该作品参与的套装规则。

## 3. 目标与非目标

**目标**

- 作品页 1 秒内给出：当前券后价、历史最低、历史分位、套装分摊价
- 任意作品（包括我们从未采集过的）都能给出历史判断
- 数据可解释：每个数字都能追溯到来源与计算方式

**非目标**

- 不做代购/下单
- 不抓登录态数据（个人券、我的页面）
- 不做全站作品的全量日更（见第 5 节，物理上不可能）

## 4. 数据源实测

### 4.1 官方接口（均已实测可用）

| 端点 | 产出 | 单次产出量 |
| --- | --- | --- |
| `/{site}/api/=/product.json?workno=X` | 当前价、定価、单品折扣、**套装字段**、活动归属 | **1 件** |
| `/{site}/campaign/discount?key=K&page=N` | 参加促销的作品 + 价格 | **50 件** |
| `/{site}/campaign/bulkbuy/=/key/K/?page=N` | 参加套装的作品 + 价格 | **50 件** |
| `/{site}/new/=/year/Y/mon/M` | 当月新作 + 价格 | **193 件** |
| `/home/api/=/coupon.json` | 全部券（含门槛、有效期、适用商品） | 538 张（游客视角 13 张） |
| `/{site}/api/=/campaignBanner.json` | 活动索引（含起止） | 4 条 |

`product.json` 里的套装字段（这是关键发现）：

```
bulkbuy_key / bulkbuy_title / bulkbuy_per_items
bulkbuy_discount_rate / bulkbuy_price / bulkbuy_start / bulkbuy_end
```

**每件作品自带它参加的套装活动、件数门槛、折扣率、以及 DLsite 算好的套装单价。**
所以不需要枚举"活动 → 商品"的映射。

### 4.2 历史序列

DLsite 不提供历史价格。我们依赖第三方公开接口（`price.maenohou.com`）：

- 覆盖：随机抽 10 件未入库作品，**7 件有历史**（其余无数据或 404）
- 深度：常见 2~218 个价格点，日粒度
- 冷启动实测：一件从未入库的作品，从请求到返回 6 个历史点耗时 **1.94 秒**

### 4.3 规模与限制（决定性约束）

| 项 | 数值 | 来源 |
| --- | --- | --- |
| maniax 分区作品总数 | **434,024** | 官方 sitemap（44 分片 × 1 万条） |
| 我方库内作品 | 20,226（4.7%） | 数据库 |
| 价格点 | 1,620,688 行 / 102 MB | 数据库 |
| `Crawl-delay` | **10 秒** | robots.txt → **8,640 请求/天** |
| 搜索结果翻页 | **禁止**（只允许 page/1） | robots.txt |
| 全库逐件轮询 | **434,024 ÷ 8,640 ≈ 50 天/轮** | 推导 |

## 5. 核心矛盾

**覆盖率 × 新鲜度 × 历史深度，三者不可兼得。**

- 单件接口 1 请求/件，`Crawl-delay: 10` 锁死 8,640 请求/天
- 全库 43 万件 → 50 天一轮，等于没有新鲜度
- 只有活动页（50 件/请求）和新作页（193 件/请求）能突破这个限制，但都只覆盖特定子集

当前采用的折中（三层）：

| 层 | 范围 | 方式 | 新鲜度 |
| --- | --- | --- | --- |
| A 活动内 | 促销期十几万件 | 活动页枚举 | 计划中，一次约 10 小时 |
| B 热库 | 2~3 万件 | 逐件轮转 | 实测 2.8 天/轮 |
| C 长尾 | 40 万+ | **首次访问按需补** | 访问即最新（1.9 秒） |

## 6. 现有实现与实测指标

| 模块 | 作用 | 实测 |
| --- | --- | --- |
| `refresh.py` | 逐件轮转刷新价格 | 7,160 件/天，2.8 天一轮（2 万件） |
| `ondemand.py` | 首次访问现场补价格 + 历史 | 1.9 秒冷启动，命中率 7/10 |
| `coupon_daily.py` | 每日为全部作品重算券后价（零网络） | 3.7 秒 / 2 万件 |
| `campaigns.py` | 活动规则与活动页抓取 | 50 件/请求，规则解析 |
| `pricing.py` | 定价纯函数 | 有效价 = 定価 ×(1 − max(单品, 套装)) |
| `backup.py` | 每日一致性快照 | 102 MB / 3.7 秒，保留 7 份 |

数据库：SQLite（WAL），单机 2 vCPU / 909 MB，读点查 0.05 ms，榜单聚合 88 ms。

## 7. 已经排除的路（附原因）

| 方案 | 结论 |
| --- | --- |
| `product.json` 批量参数（4 种写法） | 只认最后一个 workno，**无批量接口** |
| 搜索页翻页枚举 | robots 明确禁止 page>1 |
| 活动页全量枚举（3,610 页） | 可行但需 10 小时，且只有促销期有效 |
| sitemap `lastmod` 做增量 | 每分片 23 MB × 44 = 1 GB/天，且 lastmod 因简介改动也会变，噪声大 |
| 自建历史库 | 需要日更 43 万件，不可行 |

## 8. 想请教的问题

1. **有没有我们没发现的批量价格接口？** 一次返回多件作品价格（哪怕 10 件）就能把轮询从 50 天压到 5 天。
2. **`sitemap` 的 `lastmod` 是否反映价格变动？** 如果只在价格变化时更新，增量方案就成立；如果简介/标签改动也会更新，噪声太大。
3. **`Crawl-delay: 10` 是否按 User-Agent 计？** 如果按域名总量计，多进程并行就是违规；如果按 UA，是否可以注册多个 UA 合法提速（我们倾向于不做，怕被封）。
4. **历史序列还有别的公开来源吗？** 第三方接口命中率只有 7/10，剩下 30% 的作品无法回答"是否历史低位"。
5. **是否应该彻底放弃"全站覆盖"？** 即只维护"用户访问过的作品"（按需），把资源全投在活动期批量枚举上。
6. **券后价叠加套装的口径**：DLsite 官方说不叠加、取较大者，我们的实测也确认了；但"券作用在套装价上"是本站额外口径，是否有更权威的依据？
7. **架构层面**：在 `Crawl-delay: 10` 的硬约束下，是否有比"三层调度"更优的模型（比如按变化概率排优先级、或者用 sitemap 做变更发现）？

## 9. 衡量标准

| 指标 | 现状 | 期望 |
| --- | --- | --- |
| 任意作品首次访问可用时间 | 1.9 s | < 2 s |
| 热库价格新鲜度 | 2.8 天 | 1 天 |

| 活动期价格新鲜度 | 未做 | 6 小时 |
